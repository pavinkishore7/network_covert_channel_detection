# integration: pqc_auth over the namespace topology

`auth_over_topology.py` runs the `pqc_auth` re-auth exchange across the real
Phase 1 topology (`network_covert_channel/topology.py`). Before this, the
`ReauthServer` and `ReauthClient` had only talked over loopback inside one
process. Here the server and every client are **separate processes in
separate network namespaces**. They share nothing in memory, and the only
traffic between them crosses the bridge and each slice's tc shaping.

## Topology

| namespace  | address      | role                                                              |
|------------|--------------|-------------------------------------------------------------------|
| `ns-core`  | 10.200.0.2   | real `ReauthServer`, `OqsDilithiumSigner` with a persisted `key_path` |
| `ns-rogue` | 10.200.0.3   | adversary: rogue `ReauthServer` (own keypair) on :7000, replay responder on :7001 |
| `ns-urllc` / `ns-embb` / `ns-mmtc` | .11 / .12 / .13 | clients (Phase 1 slice namespaces, unchanged, tc-shaped) |

`topology.py` has no "core" namespace: in Phase 1 the only peer was the
bridge address in the root namespace. This module adds `ns-core` and
`ns-rogue` to the same bridge, using the same command shape, but **without**
tc shaping. They sit on the backhaul side, and the per-slice shaping stays
on the slice veths where Phase 1 put it. `topology.py` itself is unchanged
apart from `netns_privilege_skip_reason()`. That function is the existing
privilege probe from `tests/test_network_live_integration.py`, moved there
so both live tests share one check.

## How a client learns the server's key

Server and client no longer share an in-memory signer, so:

- **Explicit pin:** after the server starts and writes `keys/core/public_key.bin`,
  the orchestrator copies it to `oob/core_public_key.bin`, and clients get
  `--expected-pubkey-file`. **This file on the same disk only stands in for a
  real trusted channel** such as provisioning, a signed config, or a human
  comparing fingerprints. It exercises the client side of pinning. It is not
  key distribution.
- **TOFU:** clients get `--trust-store trust/<slice>.json --server-id core-reauth`
  and learn the key from the first verified response on the wire. The run
  checks that each learned key equals the out-of-band copy.

Every slice runs one batch of each, so the split is exactly half pinned and
half TOFU.

## Running it

```
python -m integration.auth_over_topology plan            # print every command; no privileges needed
sudo venv/bin/python -m integration.auth_over_topology run --report report.json

# without root: an unprivileged user+net namespace (real kernel netns/veth/bridge/tc,
# CAP_NET_ADMIN scoped to that user namespace), with a private /run for `ip netns`:
unshare --user --map-root-user --mount --net sh -c \
    'mount -t tmpfs tmpfs /run && venv/bin/python -m integration.auth_over_topology run --report report.json'
```

Integration test (excluded by default, skips with the probe's reason when it lacks the privileges it needs):
`pytest tests/test_auth_over_topology_integration.py -m integration -v -rs`, wrapped in `sudo` or in the
`unshare` line above.

Teardown always runs (`try/finally`). The orchestrator stops every process
it started, deletes every namespace and link the config describes
(best-effort, blind to how far setup got), then lists namespaces again and
reports anything left over.

## What was run, and where (2026-09-23)

The environment was WSL2 (kernel 6.6.87.2-microsoft-standard-WSL2), with no
root and no passwordless sudo. `ip netns add` fails with
`mkdir /run/netns failed: Permission denied`. **Unprivileged user namespaces
are enabled**, so the run above used the `unshare` form. The namespaces,
veths, bridge and netem/tbf qdiscs are real kernel objects. The only
difference from `sudo` is that `CAP_NET_ADMIN` applies to the user
namespace, not to the host. Results of `run` with the default 10 requests
per (slice, trust mode) batch:

- Legit batches: 60/60 requests trusted (10 per slice per mode). Every TOFU
  store learned exactly the out-of-band key.
- **Replay, same client process:** the client accepted the real response,
  then the replay responder served it the same bytes →
  `rejected_as_replay=True`, `trusted=False`.
- **Replay, fresh client process:** a new client process given the same
  captured response **accepted it** (`trusted=True`). `ReauthClient`'s
  seen-nonce memory lives only in process memory. The challenge nonce is
  generated by the server, and the client never contributes freshness, so
  any client process that restarts within the response's lifetime will
  accept a replay. This is recorded, not fixed.
- **Rogue server** (a real `ReauthServer` with a different ML-DSA-65
  keypair, answering a client that already trusts the real server):
  - pinned client → rejected via **`pinned_key_mismatch`**
  - TOFU client (store already holds the real key) → rejected via
    **`trust_store_key_changed`**
- **Link failure mid-run.** A URLLC client does 6 periodic re-auths, 0.5 s
  apart. The path is cut after 2 results and restored after 2 more. Two
  fault modes were used:
  - `blackhole` (netem `loss 100%` in both directions; the link still looks
    up): each faulted request **raised `TimeoutError: timed out` after
    ~5.0 s**, which is `ReauthClient`'s flat socket timeout. The call
    neither hung nor retried.
  - `link_down` (the slice's interface is administratively down): each
    faulted request **immediately raised
    `OSError: [Errno 101] Network is unreachable`**.
  - In both modes the exception propagates out of `request_reauth()`.
    `ReauthClient` does not catch it, retry, or return a
    `ClientVerificationResult`. The CLI wrapper records it per request. The
    next request after restore succeeded, because every request opens a
    new TCP connection. The server's served-request log shows it **never
    received** any faulted request, so no server-side schedule state was
    committed for them.
- `pqc_auth.audit_verify` on the shared client log: **73 records checked, 0
  failures, OVERALL: PASS**. That log covers the legit, replay, rogue and
  link runs; clients run one at a time, so the hash chain continues across
  processes.
- Teardown: no namespaces left inside the user namespace. Afterwards on the
  host, `ip netns list` was empty, no bridge or veth remained, and no
  `pqc_auth.transport` or orchestrator processes were left.

### Latency: what these numbers are and are not

RTT per request, measured by the client process from connect to verified
result (TCP connect + request + server ML-DSA-65 sign + response + client
verify). liboqs is imported before timing starts.

| slice | n  | min      | median   | p95      | max        |
|-------|----|----------|----------|----------|------------|
| URLLC | 20 | 8.90 ms  | 9.74 ms  | 11.53 ms | 15.70 ms   |
| eMBB  | 20 | 17.95 ms | 21.11 ms | 24.37 ms | 29.66 ms   |
| mMTC  | 20 | 28.35 ms | 31.12 ms | 44.82 ms | 1090.31 ms |

**This is veth-in-a-VM latency: signature + transport overhead on a software
topology.** It is not radio latency, not 5G latency, and it must **not** be
read against the 3GPP TS 22.261 URLLC targets as if it showed compliance or
non-compliance. Most of each number is the netem delay that
`derive_qos_profile()` *configures* (a modeling choice, not a measurement).
That delay is applied on the host-side veth, so it hits the SYN-ACK and the
response, roughly 2× the configured one-way delay (URLLC 2×4 ms, eMBB
2×8.5 ms, mMTC 2×13 ms). The remainder, about 1–5 ms, is the actual
signature + Python + TCP overhead on this machine. The one 1090 ms mMTC
sample is consistent with a lost SYN and TCP's 1 s initial retransmission
timeout under mMTC's configured 1.2% netem loss. That explanation is
inferred, not captured.

## Transport behaviour today (input for the robustness work, not fixed here)

This was measured on loopback with `pqc_auth/transport.py` as it was before
this branch, and it is unchanged by this branch except for the optional
served-request log and the CLI.

- `ReauthServer` host/port were already constructor parameters (defaults:
  `127.0.0.1`, ephemeral port). The CLI keeps loopback as its default.
- Client timeout is a flat `timeout=5.0` passed to `socket.create_connection`,
  covering both connect and every `recv`. There are no retries.
- Connection refused → `ConnectionRefusedError`, raised immediately.
- Peer closes before sending anything → `ConnectionError("no response from ReauthServer")`.
- Peer closes mid-line → `json.JSONDecodeError`, because the partial bytes are parsed.
- Peer silent → `TimeoutError` after the timeout.
- **Server side:** accepted connections have no timeout, and the server
  handles one connection at a time. One client that connects and never
  sends blocks every other client, and they time out, until it disconnects.
  A malformed (non-JSON) request raises inside the serve thread, which
  **kills it silently**. The listening socket stays open, so later clients
  connect and then time out. The CLI server detects the dead thread and
  exits with `SERVER_THREAD_DIED`.
- A client that times out may still have its request processed later by a
  busy server, which then commits that slice's schedule state. The client
  never sees the result.
